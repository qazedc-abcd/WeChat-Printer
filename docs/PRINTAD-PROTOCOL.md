# printad 协议与设备实测说明

本文整理 2026-11-05 的接口与实物研究，补充原作者未完成的探索。结论只对应当次设备、固件、素材与请求条件；没有测试到失败边界的项目只写已证下界。工具限制、服务端受理和实物输出分别说明。

本次整理所依据的研究记录共 137 次真实请求尝试：106 次 `errcode=0`、23 次字段 / 枚举拒绝、8 次设备或服务暂不可用。重复用例计入尝试数，不等同于独立用例数。未公开设备 SID、S3 凭据、完整抓包和私人小票照片。

## 1. 请求与响应

接口为 `POST https://payapp.wechatpay.cn/smartqr/printerad/printad?sid=…`，请求包含真实抓包中的 `device_sn`、`sid`、`account_type`，打印节点位于 `ad_content.user_define_template.root`。

| 响应 | 应如何理解 |
| --- | --- |
| HTTP 200 | HTTP 请求得到了响应；仍需检查业务错误码 |
| `errcode=0` | 请求受理，不证明图片下载、字段生效或完整出纸 |
| `268435461` | 本轮出现于字段类型或枚举值不合法，错误中可能包含字段路径 |
| `268697729` | 本轮同时出现于设备离线、设备正在打印、系统繁忙；需结合 `msg` 判断 |

空 root、未知节点和无法下载的图片也曾返回 0，因此工具不能仅凭接口响应确认实物成功。对超时任务不应自动重发，以免重复打印。

## 2. 已确认组件

| 节点 | 本轮观察 |
| --- | --- |
| `text` | 官方 `column[].value` / `column_align[]` 结构可打印文字 |
| `content` | 多列文本，按列对齐及权重排版 |
| `icon` | 原生二维码与远程图片 |
| `divider` | 新确认的固定横线，占一个标准行高 |

固定分隔线的已测结构：

```json
{"divider":{"style":{"justification":0,"width":0,"height":0}}}
```

本轮对照中，divider 的 width 与 justification 没有改变线长和位置；height 的实物效果未确认。当前已确认四类节点，不能由有限候选实验推断整个协议只有四类。

字段错误准确回显目标路径，是字段被识别的有力证据；反过来，不报错可能是忽略、容错或未进入相应路径，不能单独证明字段不存在。内部类型名称也不构成服务端实现语言的证据。

## 3. 图片：格式、尺寸、长图与透明通道

推荐向设备提交 `icon.type=3` 和公开的 PNG/JPEG 直链：

```json
{"icon":{"type":3,"value":"https://images.example.com/xiaopiao/image.jpg","style":{"justification":1}}}
```

| 项目 | 本轮实物 / 接口观察 | 使用建议 |
| --- | --- | --- |
| 图片比例 | 多种横图、竖图和长图被拉伸为固定方形，未保持原比例 | 上传前裁剪成方形，或按原比例放入方形白底画布 |
| 长图 | 700×6029、900×4850 等原始长图被压入一个方块 | 直接传长图不能获得等比例长条小票 |
| 图片尺寸样式 | 相同图片只改 icon.style.height/width，输出尺寸相同 | 不依赖这些字段调整图片大小 |
| 对齐 | justification 0/1/2 的左中右对照有差异 | 可用于图片对齐，具体纸宽表现以设备为准 |
| 透明 PNG | 透明区域出现黑色 | 先合成白底，再上传 |
| PNG / JPEG | 本轮可出图 | 推荐的设备输入格式 |
| GIF / WebP | 本轮无图 | 导入后先转换成 PNG/JPEG，不直接交给设备 |
| BMP | 本轮请求约 17.6 秒后返回系统繁忙 | 使用推荐格式替代 |
| 图片 URL 长度 | 已测 6000 字符可出图；12000 字符用例无图 | 优先使用短而稳定的公开直链；确切边界未知 |

GIF/WebP 不适合直接交给设备，不代表本地编辑器必须拒绝导入。当前本地裁剪会输出 PNG，QQ / Markdown 远程图片预处理输出 JPEG，原始格式会被转换。

### 工具的预处理与设备行为要分开

- 本地编辑器采用 1:1 裁剪，并可进行色调和黑白抖动处理。
- QQ / Markdown 远程图片采用 **280×280** 白底画布，保持内容比例缩放并填充，然后 Floyd–Steinberg 抖动、编码为 JPEG。这能避免设备直接拉伸原始图片。
- **20 MiB 下载 / 导入上限和 280×280 输出是本地实现策略，不是测得的设备上限。**
- 普通远程图片 URL 节点仍可直接发送原图，可能绕过白底合成、格式转换和比例修正。
- 当前工具没有长图自动切片功能。若以后切成多个方形节点，设备节点间白隙仍可能导致拼接不连续，不能承诺无缝长图。

### 图片大小与耗时：尚未测得最大值

本轮约 21 KB 的 2000×2000 极简图可处理；部分噪点图耗时明显更长，部分用例约 17.5 秒返回系统繁忙。2400×2400、约 4.5 MB 的噪点 JPEG 用例失败，不能把它列为成功下界。

图案特征与耗时存在关联，但现有实验不足以排除网络下载、格式解码、打印处理和设备状态的影响。没有测得通用文件大小或像素上限，也不能保证所有普通照片都安全。暂不以图像熵或边缘密度设置强制拒绝规则。

图床直链应无需 Cookie、Referer、登录或特殊请求头；本机能打开也不证明设备网络一定能访问。上传 Endpoint、公开域名和前缀分别配置，见 [R2 / S3 教程](R2-S3-SETUP.md)。

## 4. icon.type 与二维码风险

| type | 服务端与实物证据 |
| --- | --- |
| 1 | 本轮可生成可扫描二维码；长内容存在设备重启记录 |
| 2 | 用户先前明确报告可打印图片；本轮多次为空白，条件差异尚未解释 |
| 3 | 本轮多种图片可出图 |
| 4 | 本轮被受理，但未观察到图形 |

类型被枚举校验接受不等于可渲染；type=2 的相反观察应同时保留，等待完整 payload、素材和固件条件的对照。

**原生二维码的长内容存在设备重启风险，且服务端仍可能返回 0。** 特定 ASCII 内容的 160 长度用例正常，175、199、200、201 长度用例记录了重启；300 长度用例则出现文本输出和二维码内容不完整。不能据此推断连续的崩溃区间，也不能保证所有不超过 160 字符的内容安全。

现有 OneBot 的 100 UTF-8 字节限制是保守工具策略，不能当成硬件安全阈值。**v1.1.0 手动二维码框仍可输入较长内容，使用时请自行控制在 100 UTF-8 字节以内；不要用生产设备继续试探重启边界。** 不应通过静默截断改变二维码原意；更长信息可考虑文字或经过预处理的图片。

## 5. content：表格与字体

- 单个 content 内多条 linelist 在本轮为空白，继续使用一行一个 content 节点。
- 至少 6 列在本轮可出字；部分等权重 5/6 列布局出现末列间距偏大。权重递增 / 递减用例反映 column_width 的相对权重会生效。
- maxcolumn、column_align 数量、column 数量不一致时可能丢列。当前结果不足以确定三者的完整优先规则；程序应保持三者一致。
- 外层 content.style.height/width 多个倍率值在本轮未观察到视觉变化；这不能推广到尚未实测的 column_align[].style.height/width。
- v1.1.0 的字号预览与物理输出可能存在差异，不能以网页预览证明字号字段生效。
- Markdown 最多 16 列是本地保守检查，不是设备上限；实用排版建议优先控制在 4 列以内。

## 6. 仍待确认

root 至少 20 个有效节点的用例已被实物确认，但最大节点数、整包字节上限、文本长度上限仍未知。用户此前确认过 4096 字符文本完整打印，这同样只是对应结构的成功下界。图片最大体积、像素边界、URL 精确边界、列内字号效果和 type=2 的条件差异仍待确认。

后续验证应使用单变量和小批次，先声明耗纸预算；以响应与实物分别记录。已知会重启的用例不应自动回归或自动重试。
